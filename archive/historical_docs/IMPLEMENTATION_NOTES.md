# Phase 1 implementation notes

## Status

Implemented: a three-region slot-based simulator, variable synthetic workloads, resource and carbon/energy models, per-region observations/actions, FCFS and greedy baselines, and independent IPPO actors/critics. Phase 2.2 changes IPPO coordination so the task's source-region agent owns the decision; the environment performs feasibility and duplicate-allocation checks only. Multi-seed ablations were run as a small diagnostic experiment, not as evidence of effectiveness. This is not an exact A-MARL reproduction.

## Architecture

- `environment/task_generator.py`: immutable `Task` and six-task synthetic workload.
- `environment/cloud_environment.py`: slot arrivals, snapshot-based agent proposals, deterministic conflict resolution, finish-slot resource release, deadline feasibility, bounded deferral, allocation ledger, and interval integration of region energy/carbon.
- `environment/resource_manager.py`: capacity checks, reservations/releases, duplicate-safe allocation ledger.
- `environment/agent_api.py`: typed regional observations, candidate-region feature records, and `defer`, `execute_local`, `migrate(target_region)` actions.
- `environment/network_model.py`: transfer time from dataset size, bandwidth and RTT.
- `environment/energy_model.py`, `carbon_model.py`: shared idle-power interval integration, transparent unit conversion and time-varying carbon-intensity lookup.
- `schedulers/`: deterministic FCFS and carbon-aware placement rules.
- `experiments/evaluate_baselines.py`: repeatable small baseline run.
- `agents/actor.py`, `critic.py`: independent MLP actor and scalar value network definitions.
- `agents/rollout_buffer.py`: per-agent action traces and GAE return/advantage calculation.
- `agents/ippo_agent.py`: masked categorical actions, source-owner IPPO decisions, individual task rewards, independent PPO updates and SPT intervention.
- `experiments/train_ippo.py`, `run_phase22.py`, `evaluate_policies.py`: variable-workload training, checkpoints, baseline comparison, SPT/reward ablations, and confidence intervals.
- `results/training_seed7.jsonl`, `results/checkpoints/ippo_seed7.pt`, `results/evaluation_seed7.json`: generated training log, checkpoint and comparison output from the documented run.
- `tests/test_simulator.py`, `tests/test_ippo.py`: simulator regression and IPPO unit/integration coverage.

## Phase 2.2 coordination and task ownership

IPPO's task source region owns that task's placement decision. Only that regional policy receives the transition and reward. It chooses one masked action: defer, execute locally, or migrate to a named remote region. The environment maps the action to exactly one destination and checks it against the current candidate set, deadline, live resources and allocation ledger. The IPPO resolver does not rank destinations or select a lower-carbon proposal. Same-slot tasks are committed in deterministic task-ID order, so concurrent tasks cannot oversubscribe resources. FCFS and greedy continue to use their existing three-proposal baseline behavior.

This source-owner contract gives each agent control over tasks arriving from its own region, including migration choices. It does not model a destination region's accept/deny negotiation or independent action for every region on each task. Such negotiation would require an additional response action/state machine beyond the requested three action types.

## IPPO details and assumptions

- The agent input is a 48-value float vector: 12 normalized task/local-state values plus 12 values for each candidate region. Candidate fields are feasibility, expected carbon intensity, execution speed, execution duration, migration latency, incremental energy, estimated emissions, available GPU/CPU/memory, queue length and queued work. Normalizers are explicit fixed scales in `agents/ippo_agent.py`; resource fractions use region capacities.
- Each regional actor has four categorical logits: defer, execute at its region, migrate to remote region 1, migrate to remote region 2. Defer is always legal; other actions are masked unless the corresponding destination is feasible. The action indices use `region_names` ordering with the acting region omitted for remote slots.
- Each region has its own MLP actor and MLP value critic. PPO uses clipped ratios, entropy regularization, gradient clipping and repeated rollout epochs. GAE uses gamma 0.99 and lambda 0.95, grouped by task ID so interleaved tasks do not leak returns into each other. Deferral is non-terminal and adds `-defer_penalty`; completion and rejection terminate that task trajectory.
- Only the source owner receives the transition/reward. Completed-task reward is `-(reward_carbon_weight * min(CO2e_g / carbon_scale_g, 2) + lambda_latency * min((migration_s + execution_s) / remaining_deadline_s, 1))`; rejection receives `-lambda_sla`. Each component is logged separately. Carbon normalization defaults to 100 gCO2e, latency is normalized by remaining deadline, and values are experimental assumptions rather than a supplied Zhang formulation.
- Entropy threshold is `0.8 * log(number_of_legal_actions)`. If exceeded, the shortest-execution feasible placement is selected with configured probability 0.5. SPT-overridden samples remain in critic training but are excluded from actor policy loss, since the heuristic action was not sampled from that policy. This randomized and masked intervention differs from A-MARL's described entropy-triggered joint SPT action substitution and avoids treating heuristic actions as on-policy actor samples. Its threshold/mechanism are not claimed to reproduce the paper.
- Checkpoints contain three actor/critic/optimizer states and are seeded through Python's and PyTorch's random generators. CPU is the default for Windows portability. Every training episode is generated from a reproducible variable synthetic workload; configured evaluation seeds are held out.
- Training/evaluation logs include episode metrics, each controlling agent's action/mask/probabilities, selected action/destination, individual reward components, entropy, SPT overrides, and resolver interventions.

## Model assumptions

- Slots are 60 seconds. Runtime and migration are conservatively rounded up independently to slots for reservation and deadline checks.
- Deadlines are absolute seconds from simulation start; task runtime is modeled as a scalar independent of resource size. A production model should use per-region throughput and actual traces.
- Default inter-region links use 2 Gbit/s and 80 ms RTT when no link is specified. These are placeholders, not empirical data.
- Energy is integrated over task active intervals. GPU dynamic power is summed across concurrent tasks; region idle overhead is charged once whenever at least one task is active. PUE multiplies both. Totals are aggregated by region and are also used as incremental placement costs for the greedy scheduler.
- Carbon intensity is piecewise constant by simulation slot and can vary by region and time. Synthetic profiles are in `configs/cloud_config.yaml` and `experiments/evaluate_baselines.py`; after a profile ends, that region's configured default intensity is used. No real carbon data is bundled. CO2e is calculated in grams.
- Region execution speed is a relative multiplier: effective runtime is task runtime divided by regional speed. The configured factors are illustrative and affect both finish slots and deadline feasibility.
- Deferral is bounded to two slots. A task with no feasible resource after that is rejected. Baseline greedy selection uses a 0.01 seconds-to-grams heuristic coefficient; the IPPO reward is separately defined above.
- IPPO has one controlling proposal per task from its source-region agent. Baseline schedulers retain simultaneous proposals; their resolution behavior is unchanged. Task IDs are claimed once, and resource reservations are serialized.
- Observations contain slot, region ID, task, available GPU/CPU/memory, local feasibility, feasible destination names and local carbon intensity. They omit queue forecasts, future carbon forecasts, network details and global state; action space is defer, execute locally, or migrate to one named destination.

## Phase 2.2 coordination redesign

The task's source-region agent is the only policy that acts on that task. It selects defer, local execution, or migration to a named remote region. The environment only validates the selected target against current feasibility/deadline/resource constraints and prevents duplicate task allocation. It does not choose among proposals by carbon. Same-slot tasks are serialized by stable task ID to keep resource reservations safe. Other region agents have no losing proposal and receive no transition for that task.

Each source-agent observation has 48 normalized values: 12 task/local-state values and 12 values for each candidate region. Candidate data includes feasibility, carbon intensity at expected execution start, relative speed, execution duration, migration latency, estimated incremental energy/emissions, available GPU/CPU/memory, queue length and queued work. Candidate slots follow the simulator's stable region ordering. The four-action mask retains defer, local, and the two remote targets.

Reward is assigned to the task owner only. Defer gives `-defer_penalty` and is non-terminal; completion and rejection terminate that task's trajectory. A rejection is distinct from deferral and receives `-lambda_sla`. Each task has its own rollout trajectory ID, so GAE does not connect unrelated arrivals that are interleaved in the episode. The per-decision trace records reward components and terminal state.

Training tasks are produced by `generate_variable_workload(seed, task_count)`, independently of the original six-task demo. The Phase 2.2 runner uses held-out workload seeds that do not overlap the training seed construction. `run_phase22.py` runs the SPT/full-reward variant, no-SPT variant, carbon-only reward and latency-only reward across multiple policy seeds, then compares FCFS/greedy/IPPO on matched workloads. Its confidence intervals use a small crossed-cluster bootstrap; exact methodology and limits are in `results/phase22/PHASE22_REPORT.md`.

This differs from A-MARL in the environment, action semantics and SPT intervention. A-MARL's authors describe entropy-guided joint SPT substitution on a job-shop task. Here the source-region IPPO policy owns one cloud placement decision; SPT can probabilistically override that owner action, and overridden samples are excluded from actor loss. No exact reproduction is claimed.

## Phase 2.3 reward design and validation

Phase 2.2 artifacts and report are historical and remain unchanged. Phase 2.3 uses normalized reward terms. For an execution, `R = 1 - 1 × min(max(C,0)/100,2) - 0.25 × min(max(L,0)/max(D,1),1)`, with emissions `C` in gCO2e, latency `L` in seconds, and remaining deadline `D` in seconds. The fixed completion credit is `+1`; carbon is the primary variable cost and can contribute at most `-2`; latency is a smaller service cost bounded by `-0.25`. Thus the lowest feasible execution reward is `-1.25`. Rejection gives `-(2.5 + 0.5) = -3`, where `2.5` is the explicit rejection penalty and `0.5` is the SLA penalty. These configured values satisfy validation that rejection is worse than any feasible execution.

Each continuing defer costs `-0.1`. At the existing two-deferral limit, if the policy still defers and at least one region remains feasible, the simulator completes the workload with a feasibility-only fallback: use its source region if feasible, otherwise the first feasible region in stable configured order. This fallback does not compare emissions. The agent receives `-1.5` for its deferred decision, no completion bonus, and a terminal transition; this is worse than the bounded feasible execution score. The environment rejects only if no placement remains feasible. Only the task's source agent receives the transition/reward. Resolver intervention and forced completion are included in decision logs. This design guarantees service for a still-feasible task, even if a short-trained policy would otherwise defer repeatedly.

The `ippo_carbon_only` ablation sets latency weight to zero; `ippo_latency_only` sets carbon weight to zero. Both retain completion, SLA, rejection and deferral terms, so the ablations do not reward abandoning tasks. `ippo_no_spt` disables SPT. All other settings are shared. No architecture switch or tuning to the original six-task workload was made.

## Phase 2.6 centralized critic pilot

`agents/mappo_agent.py` implements a MAPPO-style comparison while preserving `IPPOScheduler` and the Phase 2.5 artifacts. All three actors remain independent and decentralized. The shared centralized critic is trained from source-owner transitions and receives the concatenation of each region's 54-value task/candidate observation plus a three-element acting-agent one-hot. This is centralized training only; deployment actors still receive their own regional observation. Masks remain feasibility-based, and only the source agent receives the task's reward. Shared critic values are stored in the existing per-task GAE buffer. Its critic loss, gradient norm, and pre-update explained variance are logged separately from per-actor loss, entropy, gradient norm, and parameter update size.

The simulator already creates all three regional observations from one decision snapshot. For MAPPO the environment passes that complete snapshot to `propose_global`; the IPPO and baseline call paths remain unchanged. The existing safety resolver still rejects stale/infeasible actions and serializes commitments. SPT is the same configurable entropy-triggered shortest-execution override used by IPPO; this implementation does not claim A-MARL reproduction. The centralized critic changes the value function and its training data, not the scheduling objective, reward, policy algorithm, or actor parameter sharing.

## Phase 2.8 offline optimisation benchmark

`experiments/offline_optimizer.py` implements an exact small-instance mixed-integer linear program using SciPy `milp`/HiGHS. `requirements.txt` now includes SciPy. Binary variables choose one region and decision slot per task; the feasible slot window is arrival through the same two-slot deferral limit used by the simulator. Constraints enforce full completion, GPU/CPU/memory reservations until the simulator's finish slot, migration-adjusted absolute deadlines and unique task placement. Energy/carbon costs are linearized into GPU-active power per execution interval plus a binary shared-idle indicator per region/interval. Intervals split at all possible execution boundaries and carbon-slot boundaries. Thus a solver `optimal` status is exact to solver tolerance for the current energy/resource model. Time-limited feasible incumbents are explicitly labelled and excluded from certified optimality gaps.

The optimizer is offline and uses the whole task set plus the full synthetic carbon profile. FCFS and greedy carbon run through the original simulator as online policies; no lookahead or scheduler change was added to them. The result is consequently an oracle lookahead benchmark, not a like-information online algorithm comparison. It uses the environment's `_integrate_region` to independently recompute selected schedule energy and emissions; tests compare a one-task MILP to exhaustive region/slot enumeration and validate multi-task capacity/deadline/resource constraints and exact integrated totals.

`python -m experiments.run_phase28` ran sizes 4, 8 and 12 with seeds 28101, 28102 and 28103 (9 instances). All 9 MILPs were certified optimal, and greedy, FCFS and offline schedules completed all tasks with zero rejection/SLA violations. Average greedy emissions gaps were 6.51% [bootstrap CI 1.00–10.83] at 4 tasks, 13.09% [3.20–26.98] at 8 tasks, and 9.05% [2.84–17.06] at 12 tasks. The unweighted mean of the nine per-instance gaps was 9.55%. Across seeds, mean emissions (offline / greedy / FCFS) were 91.53 / 99.66 / 141.27 g for 4 tasks; 74.02 / 84.51 / 165.65 g for 8; and 140.94 / 154.29 / 305.98 g for 12. Mean MILP wall time was 0.012, 0.015 and 0.120 seconds respectively on this host; greedy simulation was about 0.001, 0.0015 and 0.0031 seconds. See `results/phase28_final/PHASE28_REPORT.md` and machine-readable evaluation files for energy, latency, service and per-instance values/CIs.

The measured gap is moderate rather than negligible on these scenarios, so it warrants investigating a **safety-gated contextual bandit or forecast-aware heuristic**. It does not establish that learning is justified: the offline optimizer knows future tasks and carbon, whereas greedy does not; the small samples use synthetic workloads and profiles; and the gap may mainly be the value of two-slot temporal lookahead, not a misranking that bandit feedback can learn. First separate those sources (perfect-forecast online heuristic, no-wait offline assignment, and capacity-only lookahead ablations) and expand held-out cases. The current greedy remains unchanged and prior results remain preserved.

## Phase 2.9 contextual bandit pilot

`agents/contextual_bandit.py` implements per-destination disjoint LinUCB. Its 12-value context consists of a bias, current candidate carbon intensity, incremental emissions and energy, execution and migration time, current GPU/CPU/memory availability, queue length/work and deadline fraction. It receives only the current task observation and feasible candidate list; it does not receive the task stream, future arrivals, or future carbon profile. The selected region is masked by the simulator's live feasible set and revalidated against its deadline/resource candidate. A low-confidence alternative falls back to the known immediate greedy reward; invalid model output or a stale/infeasible destination also invokes the greedy baseline. No candidate means the simulator's original deferral/rejection lifecycle applies, not a fictitious feasible fallback.

The bandit updates only the selected and actually committed arm, with the normalized service-aware execution reward, at the end of each episode. Training uses seeds 17, 29, 41; 12 episodes and 12 tasks per episode; held-out evaluation uses six distinct workload seeds and dynamic synthetic profiles. Evaluation freezes the trained parameters. Logs include per-candidate metrics and LinUCB estimates, selected and actual destinations, greedy choice, reward/payoff, update indicator, fallback reason/frequency, arm counts and coefficient norms. `experiments/run_phase29.py` also evaluates FCFS, greedy, and the Phase 2.8 offline MILP on identical held-out workloads.

The pilot did **not** meet the stated success criterion. Across 18 training-seed × held-out-workload runs, contextual bandit emissions were 227.43 gCO2e versus greedy 225.83 g; the service-matched paired difference was +1.60 g [95% bootstrap CI 0.00, 4.00] (n=18), not an improvement. Mean completion and SLA counts matched greedy (98.61% completion and 0.167 SLA rejections per workload); the one rejected task per policy occurred on the same overloaded held-out workload (seed 29101), for which the offline all-completion MILP was infeasible. Bandit energy was 0.889 kWh versus greedy 0.894 kWh, and latency 250.01 s versus 250.21 s; these small metric differences do not establish an objective improvement. Mean greedy fallback rate was 4.76% of bandit decisions. On five workloads with feasible certified offline solutions, the bandit's mean gap to offline was 9.43% [6.80, 12.21], while greedy's was 7.80% [4.58, 11.13]; these are oracle-lookahead comparisons and not online-policy regret. Full results and confidence intervals are in `results/phase29_final/PHASE29_REPORT.md`.

The contextual bandit therefore does not demonstrate an advantage over greedy. Retain greedy as the operational scheduler. Before any further learner, isolate the effect of known future carbon/arrivals and add workload families where an online decision's future capacity externalities are material. The bandit cannot guarantee completion under arbitrary overload; it preserves the same immediate feasibility/deadline safety and is evaluated against greedy's actual service metrics. The Phase 2.9 pilot outputs/checkpoints are preserved under `results/phase29_final/`.

## Phase 3 real-trace integration

`experiments/preprocess_phase3.py` uses the verified official DCcluster-Opt/SustainCluster processed Alibaba GPU task archive and three official 2023 Electricity Maps carbon series (NYISO, CAISO, ERCOT) from SustainCluster. It keeps downloaded source files under `data/raw/phase3/`, hashes them, and writes bounded deterministic task and carbon JSON under `data/processed/phase3/`. Full source, schema, units, licenses, actual download sizes, hashes, and provenance are recorded in `data/DATA_SOURCES.md`. No original research repository is modified.

The workload subset contains 24 source tasks in three non-overlapping 24-hour windows, eight tasks per window. Arrivals use `interval_15m`; duration minutes convert to seconds; source CPU/GPU percentages are divided by 100 into fractional core/GPU units; memory and bandwidth-derived GB remain unchanged. A fixed 3,600 second slack is added to runtime because the source does not include task deadlines. The source has no geo-origin field, so all tasks enter through north (NYISO) as an explicit scenario assumption. The bundled processed trace reports 37,552 intervals from 2020-01-01 through 2021-01-26, despite the Alibaba source description of July–August 2020; packaged timestamps are used and the discrepancy is documented. The selection is the first eligible source task in evenly spaced 3-hour bins, with runtime ≤2h and resource demands bounded by north ingress capacity.

Carbon traces are hourly 2023 direct gCO₂e/kWh series, repeated across four 15-minute slots using zero-order hold. Fifty-one source rows are flagged estimated (NY 49, CA 2, TX 0); those marks are preserved. Missing values and nonhourly timestamps fail preprocessing; no interpolation or missing-value fill is performed. Workload dates (2020) and carbon dates (2023) are overlaid by replaying from the first carbon observation and are not calendar matched. Region keys map north=NYISO, west=CAISO and east=ERCOT; capacities, GPU power, idle power, PUE, execution speeds and network characteristics remain inherited model assumptions.

To prevent future-carbon leakage, `CarbonModel.candidate_forecast_known=False` makes real-trace candidate features use only the current intensity observation (held flat for the estimate). Full time-varying historical carbon remains in outcome accounting and in the offline MILP. The offline solver therefore has explicit future lookahead and is not an online baseline. Phase 2 synthetic default behavior is unchanged. The selected traces are evaluated against three same-size synthetic workloads on the same real carbon profiles; prior Phase 2 results are preserved.

The small run (`python -m experiments.preprocess_phase3`; `python -m experiments.run_phase3`) selected 24 real jobs and solved all three trace-instance MILPs optimally. Greedy emissions averaged 437.97 ± 512.56 gCO₂e with 100% completion, zero rejection/SLA violations, and mean latency 2,476.09 s; its mean gap to the offline MILP was 3.28% [1.08, 4.45]. FCFS averaged 533.66 ± 646.95 gCO₂e and a 20.89% offline gap. Synthetic comparison greedy averaged 207.23 ± 97.39 gCO₂e and matched MILP on all three instances. These intervals use only three instances and are descriptive; the workload and carbon years are unsynchronized, deadlines are assumed, the job subset is small/selected, and network/power/resource configuration is not empirically calibrated. This is simulated-trace evidence only, not real-world cloud effectiveness. No RL algorithm was added. The report and machine-readable outputs are in `results/phase3/`.

## Phase 3.3 forecast-aware receding horizon (MPC) benchmark

`schedulers/forecast_mpc.py` implements `ForecastAwareMPCScheduler` and the bounded `CarbonForecastProvider`. Lookahead is configured independently of the retry transition budget: the corrected 2h and 4h policies inspect up to 8 and 16 fifteen-minute slots respectively, while both allow two defer transitions. A defer can commit directly to a later feasible retry slot; it does not implicitly consume one transition per elapsed slot. Forecast queries outside the configured horizon raise `ValueError`.

Reservation lifecycle: a deferred task records its destination, target slot, and resource interval, including migration time and rounded execution occupancy. The environment assigns the task only to that region at the committed slot. Capacity checks account for GPU, CPU, and memory overlap with known assignments and other reservations. The environment uses a scheduler-aware final slot bound, rejects any run that leaves a task nonterminal, and releases a reservation on placement, rejection, expired target, or rescheduling after a live conflict. Tests cover reservation handoff, conflicting allocations, reservation cleanup, extended deferral budgets, deadline handling, and distinct 2h/4h lookahead capability.

The corrected benchmark uses the same 78 Phase 3.2 workload instances and matched 12-task prefixes. Final artifacts are versioned at `results/phase33_corrected_v5/`; prior original/corrected result folders were preserved. Accounting reconciles the matched prefix to 24 family/window cases × 5 online policies = 120 online rows, plus one MILP row per case = 144 rows total. Full-size accounting is 78 instances × 5 online policies = 390 rows. Of 24 MILP runs, 17 certified optimal and 7 returned feasible incumbents; optimality gaps are reported only where valid.

In the corrected 78-instance paired comparison, corrected MPC (2h) versus greedy had mean emissions difference −31.36 gCO₂e (95% bootstrap CI [−54.02, −14.61]) and mean emissions per completed task difference −1.04 gCO₂e ([−1.64, −0.60]). The paired energy difference was −0.053 kWh (95% CI [−0.136, +0.009]); completion-rate difference was −0.0011 ([−0.0048, +0.0024]); SLA-violation difference was +0.013 ([-0.141, +0.141]). Corrected MPC 4h matched 2h exactly: 78/78 identical decision signatures. Thus the benchmark does not demonstrate a horizon effect or universal MPC superiority. On the 48-task burst family, corrected MPC completion averages 0.93 versus greedy 0.92, with mean emissions 943.04 versus 1,005.47 gCO₂e; interpret emissions alongside completion, rejection, and SLA counts. The 95% intervals describe these selected package-axis scenarios, not a broad deployment population.

The workload deadlines are derived as runtime + 3,600 seconds, which may not give enough feasible slack to distinguish the horizons. Region capacities are static. Live checks protect against known resource conflicts, but future arrivals are unknown; a conflict may cause a committed task to be rescheduled. Online scheduler decisions use only current state and bounded carbon forecasts, while offline MILP has lookahead and is a benchmark rather than a deployable comparator. The earlier false burst-48 completion claim is superseded. See `PHASE33_AUDIT.md`, `PHASE33_CORRECTED_REPORT.md`, and the superseded original report retained at `results/phase33/PHASE33_REPORT.md`.
